Engine internals (as of 2026-08-16) so difficulty/AI changes don't require re-reading the engine sections.

**Chess (`js/chess.js`, "Engine" section ~line 66):**
- `new Worker("engines/stockfish-18-lite-single.js")` (document-relative path). Plain UCI text protocol over `postMessage`; replies matched by an `expect(pred)` promise queue over `onmessage` lines. Boot sends `uci` and waits for `uciok`; worker construction fails on `file://` and shows a "serve over HTTP" message.
- Difficulty (`configureEngine(elo)`): Stockfish's calibrated floor is **1320 Elo** — at ≥1320 it uses `UCI_LimitStrength`/`UCI_Elo`; below that it uses `Skill Level` = `clamp(floor((elo-600)/100), 0, 7)`.
- Two extra weakening knobs: `moveTimeMs(elo)` scales 80ms→1000ms, and `randomMoveChance(elo)` blends in random legal moves below ~900 Elo (~88% random at the 200-Elo default) because Stockfish can't get weak enough alone.
- Live evaluation ("Live evaluation" section ~line 112, opt-in via the `engine-eval` storage flag): when enabled, the engine analyses continuously on the player's turn (`go infinite`, started after each player-facing render and stopped before every engine search) and the first `info … score` line received per position paints a lichess-style bar (`#eval`) under the board. Scores come back side-relative (`searchTurn` flips the sign); mate scores are stored as ±1e6 plus a signed mate count shown as `Mx`/`m-x`. `parseScore` rewrites `evalWhite`/`evalMate` on every line, so the bar tracks the deepening search in place. The eval bar never touches gameplay: `engineMove` always stops the analysis first (`stopAnalysis`), and game over frees the worker. `stopAnalysis` posts `stop` then drains the analysis `bestmove` via `drainBestmove()`, which abandons the wait after 1.5s (and removes its waiter) so a `go infinite` that never answers "stop" — seen around mating lines — can't hang the engine's next move.

**Checkers (rules + engine in `js/shared/checkers-engine.js`; `js/checkers.js` is the UI):**
- Board is `number[8][8]`: 1 red man, 2 red king, -1 black man, -2 black king, 0 empty. `RED = 1`, `BLK = -1`; red starts at the bottom (rows 5–7), moves up (decreasing row), and moves first. Kings crown at `CROWN_ROW = { RED: 0, BLK: 7 }`. 80 plies without capture/man-move = draw (checked by `js/checkers.js`, not the engine).
- Engine: negamax + alpha-beta + iterative deepening from depth 2, plus a **transposition table** (`Map`, Zobrist-keyed; two independent deterministic 32-bit LCG tables `ZLO`/`ZHI` make a 64-bit key, Map keyed on `lo` with `hi` verified on hit so a collision is a miss, never a wrong move; capped at `TT_LIMIT = 200000` and cleared when full). Entries store `{ side, depth, score, flag, move }` with `flag` 0 EXACT / 1 LOWER / 2 UPPER; probe returns on matching `side` + `depth >= depth`, and the stored best move is tried first for move ordering. Mate scores encode distance-to-mate as remaining depth (`-50000 - depth` for a no-moves loss — later losses score less negative, quicker wins higher), so probes re-base scores with `|score| > 40000` by `ent.depth - depth` to keep distances comparable (both engines, added 2026-08-13). `negamax` also enforces a `performance.now()` deadline by throwing a `TIMEOUT` symbol (search runs on a private board copy because the throw skips `undoMove`). Quiescence: depth 0 keeps resolving forced captures. `evaluate` is material (man 100, king 175) + advancement + center bonus, positive = good for red.
- **Both engines were speed-optimised 2026-08-13 — connect four 1.69M → 2.91M nodes/sec (+72%), checkers 0.77M → 1.20M (+56%), with output verified bit-identical.** Three changes, applied to both: (1) the Zobrist key is **incremental** — `negamax(bd, side, depth, alpha, beta, lo, hi)` takes the key as two plain numbers and each child XORs in only what changed, so `zobrist(bd)` (a full 42- or 64-cell rescan) now runs once per move at the root instead of once per node. In checkers the delta is computed inside `applyMove` and returned on the undo record as `u.zlo`/`u.zhi`, since that record already names every square that changed; in connect four it is one table lookup, `zAt(r, c, side)`. (2) Direction tables are two flat arrays `DR`/`DC` instead of arrays of pairs — `for (const [dr, dc] of DIRS)` destructured on every step of the hottest loop, and in connect four's `isWinAt` the inner `for (const s of [1, -1])` **allocated a fresh array 4× per call**, roughly 50M throwaway arrays/sec. Checkers' `MAN_DIRS`/`KING_DIRS`/`CROWN_ROW` side-keyed objects are gone too (`dirFrom`/`dirTo` index into `DR`/`DC`; `crownRow(v)`); **the direction order is load-bearing** — it is move-generation order, which is search order. (3) Connect four precomputes the 69 scoring windows into a flat `Int8Array` (`WINDOWS`) at load, so `evaluate` walks it instead of bounds-testing 168 candidates per call; checkers' undo record stores captures as flat `(r, c, value)` triples instead of an array per capture. `undoMove` and the undo-record shape are engine-internal — `js/checkers.js` only imports `genMoves`/`applyMove`/`sideOf`/`isMan`/`aiPickMove`, and `applyMove` still accepts a plain `{ path, caps }` built by the UI.
- Both the AI's move and the live eval run through the same Worker (`askEngine` in `js/checkers.js`; protocol `{ id, board, side, level, ms } → { id, move }`), sharing the one transposition table — so the eval search warms the AI's next move. If the Worker can't start (e.g. `file://`), `askEngine` degrades to calling `aiPickMove` synchronously on the main thread.
- `LEVELS[0..9]` table drives the 10 difficulty levels: `{ label, depth, ms, noise, random }` — depth 1→15, time budget 60→2000ms (ramped up from 60→1300ms; high levels are time-capped, not depth-capped — at 2s level 10 reaches effective depth ~8–11 in middlegames vs depth 3 for level 4, and extra budget beyond ~1s buys little because per-ply cost grows exponentially), `noise` widens the pool of near-best moves picked from at random, `random` is the chance of playing any legal move (0.85 at level 1, 0 from level 4 up) so young kids can win. Iterative deepening caps at the level's `depth`. The noise margin drops to 0 when the best score is decisive (`|score| ≥ 40000`) — win/loss scores differ by only 2 per ply, so noise used to lump every losing move together and a lost AI played randomly instead of blocking (both engines, fixed 2026-08-13).
- Live evaluation ("Live evaluation" section in `js/checkers.js`, opt-in via the `engine-eval` storage flag): the player's turn ends by scheduling `quickEval` 250ms after the "Your move" render. It calls `askEngine(playerSide, EVAL_LEVEL, EVAL_MS)` — `EVAL_LEVEL = 9` (LEVELS[9]: depth 15, though the `EVAL_MS = 300` short override is what actually bounds it, so a pending eval never delays the AI's own move request queued behind it) — and paints the reply's `.score` on the `#eval` bar (side-to-move-relative, which on the player's turn means player-relative; `random` is 0 at that level so the score is exact minimax). Stale replies are dropped via a `gameSeq` counter bumped on start/undo. Fixed 2026-08-13: `paintEval` used to negate the score for a Black player, showing the bar backwards — the score is used as-is now.

**Connect Four (rules + engine in `js/shared/connect4-engine.js`; `js/connect4.js` is the UI):**
- Board is `number[6][7]`: 1 red, -1 yellow, 0 empty; `board[0]` is the TOP row and a disc lands on the highest-indexed empty row (`landingRow`). `RED = 1` moves first. Draw = full board (no move clock). `winLine(bd, r, c)` returns the winning cells through (r,c) for the UI's highlight; `isWinAt` is the allocation-free variant the search uses.
- Engine: deliberately the same architecture as checkers — negamax + alpha-beta + iterative deepening from depth 2, TIMEOUT-symbol deadline on a private board copy, and a Zobrist transposition table (`ZLO`/`ZHI` 32-bit LCG pairs, Map keyed on `lo` with `hi` verified, `TT_LIMIT = 200000`, entries `{ side, depth, score, flag, move: col }`). Moves are generated centre-first (`ORDER = [3,2,4,1,5,0,6]`) for sharper cuts. Each node first checks whether any legal reply wins on the spot and returns `50000 + depth` (prefers faster wins and later losses, keeps the search out of finished positions); an immediate root win scores `1000000`. TT probes re-base mate scores and the noise margin skips decisive scores, exactly as in checkers (see above). `evaluate` scores every 4-cell window only one side occupies (three = ±50, two = ±10, one = ±1) plus ±5 per centre-column disc; positive = good for red.
- Worker protocol identical to checkers: `{ id, board, side, level, ms } → { id, move }` where `move` is `{ col, row, score }` or null (`score` is the best root score, side-to-move-relative); same `askEngine` wrapper and sync `aiPickMove` fallback for `file://` in `js/connect4.js`.
- `LEVELS[0..15]` — **16 levels** (was 10, widened 2026-08-13; `connect4.html`'s slider is `max="15"` and `js/index.js` prints "of 16"). `{ label, depth, ms, noise, random }` — depth 1→42 (42 = every square, i.e. perfect play if a search ever finishes it), time budget 60→4500ms, `random` fading 0.90/0.70/0.45/0.28/0.15/0.07 over levels 1-6 then 0, noise 240→0. Noise margin = `noise * 3` around the best score (0 when the best score is decisive). Labels are descriptive ("beginner"…"good luck!"), not Elo. Old saved prefs stay valid because the level is just an index that still exists; levels don't map 1:1 to the old table (old 10 ≈ new 13).
- Root move choice in `aiPickMove` breaks ties in three stages: score, then distance-to-mate (both via the `50000 + depth` encoding above), then **defence** (added 2026-08-13). The defence stage only runs when every candidate scores *exactly* the same — which is the lost-position case, since a decisive score forces `margin = 0`, and it deliberately skips the widened noise pool at low levels so their weakening survives. It ranks each candidate `(blocks a live opponent finish ? 100 : 0) − (opponent finishes still available afterwards)` using `winningCols(bd, who)` (new rules helper: the columns where `who` completes a four right now), then picks at random among the joint best. Without it the AI played a uniformly random column whenever the player had a double threat or a three that just restacks on top of the blocking square — every move genuinely does lose on the same ply, so score and depth both tie. Ranking is computed on a fresh copy of `bd0`, **not** the search's `bd`: a TIMEOUT throw skips `undoMove` and leaves phantom discs on it.
- **Tried and rejected 2026-08-13 — don't redo this.** Packing the tiebreaks into one score (`eval × 1e6 + depth × 1e3 + blocks`, or the equivalent lexicographic tuple) instead of the root tiebreak above. It does not fix the lost-position bug: the `if (win) return 50000 + depth` short-circuit fires *before* the leaf eval, so in exactly the decided positions that need it, a band living in `evaluate` is never reached — measured at 38/120 and 28/120 blocked, i.e. chance. It also requires rescaling six engine constants plus `LEVELS.noise` and the eval bar in `js/connect4.js`, with a silent failure mode (miss one and a positive eval reads as a forced win: the search collapsed from 11M nodes to 111). The root cause is structural: blocking is a property of a *move*, and negamax scores *positions*.
- **Also tried and rejected the same day:** three leaf-eval improvements, all measured by move-quality against a depth-11 oracle over 500 random positions at two shallow depths. (1) Exact fork detection at the leaf — if the side to move has no immediate win and the opponent has ≥2 live finishing columns, the opponent wins next turn, so return `-(50000 + depth - 1)`. The logic is provably correct and it still measured 12 better / 14 worse, because it is a *selective* extension: it deepens only lines that are provably lost while sibling leaves keep a static eval, which biases the backed-up values. Note the immediate-win loop already detects forks at depth ≥ 1, so this only ever added vision at the final ply. (2) A smooth `-threats × THREAT` leaf penalty at weights 10/25/50, capped and uncapped — swung 70% → 49% → 41% across depths and seeds, i.e. noise, and it double-counts the ±50 `evaluate` already gives a three. (3) Making the window score gravity-aware (weight a three by whether its gap is at the column's landing row) at four live/buried weightings — all 44–57%, inside noise. Cost measured for reference: a per-node block count is ~30% of node throughput (1.88M → 1.31M nodes/sec), leaf-only ~10%.
- The UI shortcuts forced replies: `obviousMove()` in `js/connect4.js` tries every legal column for both sides and, if anyone would make four in a row, passes `ms = min(level.ms, 400)` to `askEngine` and skips the hand's wavering. Verified 2026-08-13 that a 400ms cap picks the same blocking column as the full 4500ms level-16 search (the reply is forced, so depth can't change it), and that an available win returns in ~0ms via the root `1000000` shortcut.
- Live eval mirrors checkers: `EVAL_LEVEL = 10` (LEVELS[10]: depth 14), `EVAL_MS = 300`, 250ms `scheduleEval` delay, `gameSeq` staleness guard; the bar maps score via `100/(1+e^(-0.01·mine))` clamped to 3–97% and shows a text callout instead of a number when `|score| ≥ 40000` (forced win found).

**Chinese Checkers (geometry + rules + engine in `js/shared/chinese-checkers-engine.js`; `js/chinese-checkers.js` is the UI):**
- Board is a **flat `number[121]`**: the star in cube coordinates (x + y + z = 0), on-board iff inside either big overlapping triangle ({x,y,z ≥ -4} ∪ {x,y,z ≤ 4}) — a 61-cell central hexagon plus 6 corner triangles of 10 (`TRI[k]`). Cell order is z (outer, -8→8) then x ascending, i.e. top-to-bottom rows on screen; `IDX[(x+8)·17+(z+8)]` maps coords → cell index. Values: 0 empty or player id 1–6 (id = home corner + 1; the human is always 1, bottom corner, moves first; `targetOf(p) = (p+2)%6`). Seatings: `SEATS = { 2: [1,4], 3: [1,3,5], 4: [1,2,4,5], 6: [1..6] }`. `NBR`/`JMP` are flat `Int16Array(121·6)` one- and two-step neighbour tables over `DIRS = [(1,0),(1,-1),(0,-1),(-1,0),(-1,1),(0,1)]` as (dx, dz).
- Rules (per geekyhobbies.com, plus one owner-requested restriction): a turn is one step to an adjacent empty hole OR a chain of hops over any adjacent marble (own or opponents') into the empty hole directly beyond — direction changes fine, stop anywhere legal, **nothing is captured**. **A move may not END inside a corner triangle other than the mover's own home or their target** (`canRest` in `genMoves` filters emitted destinations only — hopping *through* a foreign corner mid-chain stays legal, and the search/hint-dots/drag all inherit the rule from `genMoves`). **Win = your target triangle is completely full AND at least one marble in it is yours** — the anti-blocking rule: the owner's parked marbles count as filled for the incomer, so parking hands the win over instead of making it unreachable. (At the start the target is full of the owner's ten with none of yours, so nothing fires until they vacate a hole and you claim it; in 3-player games targets are corners only the incomer can rest in, so it reduces to the plain all-10 win.) A win can therefore be triggered by the *owner's* move (re-filling their home's last hole): after any move by p the only possible new winner is p or the player targeting p's home — the exported `winnerAfter(bd, mv, p, teams)` checks exactly those two, and the UI calls it after every move. No draw clock, no destination-triangle lock (marbles may leave the target again).
- **Teams** (optional for 4/6 players, per the consulted rules): partners are opposite-corner pairs — `partnerOf(p) = targetOf(p) + 1` — so 4p = (1,4)+(2,5), 6p = (1,4)+(2,5)+(3,6), and the human's partner is always the top AI (seat 4). Because your target *is* your partner's home, the anti-blocking squatter rule is OFF in team games (it would award wins for swapping two marbles); the team wins when **both partners are strictly done** (`isDone`: all ten target holes hold that player's own marbles). Only the mover's own team can complete on the mover's move. A finished player must still move (no pass rule) — they're forced to step out of their full triangle and back in, so they're "done" on the rounds between their own turns and the double-done check succeeds at most one round late; self-play confirms team games end. In the search, `teams` makes every mover maximise `vec[p] + vec[partner]`, `terminalVec` spikes both winners' entries, and TT entries carry a `tm` flag verified on probe — team and free-for-all searches back up different values for the same position and the table outlives games. The Worker protocol gains the flag: `{ id, board, side, level, ms, teams }`.
- Move = `{ from, to, path }`; only the destination matters, so `genMoves` emits per-marble steps then a BFS over hop landings (the moving marble's own hole is emptied for the chain and marked visited so it can't be a destination), deduped by destination with a step preferred over a chain to the same hole. Scratch arrays (`visAt`/`seenAt`/`parent`/`queue`) are generation-stamped Int32/Int16, never cleared. `applyMove` returns the moved value; `undoMove(bd, mv, v)` takes it back.
- Search is **max-n, not negamax** (2–6 players): `search(bd, seatIdx, depth, lo, hi)` returns a `Float64Array(7)` score vector and each node's mover maximises their own entry. No alpha-beta — it's unsound in max-n — so speed comes from the transposition table plus per-node move caps: the root side keeps `k` moves per node (8–16 by level), opponents `kOpp` (3–8), the root itself `max(2k, 16)`; moves ordered by `gain` (DIST-to-target-tip reduction), TT best move front-loaded. A fully blocked seat passes the turn (recurses to the next seat).
- `evalAll` (one score per player): Σ per marble `(16 − hexdist-to-target-tip)·10` + 14 per marble already inside the target triangle, − 6·(distance of the most-lagging marble). One forward step ≈ +10. A win (the mover's own, or one gifted via `winAfter`) is detected immediately after each move with no recursion past a finished game; `terminalVec` gives the winner `+100000 + depth·100` and every other seat the same amount *negative* (quicker wins, later losses), so the search chases wins, blocks other players' wins, and never re-fills its own home when an incomer squats inside (the root scores such a gift `-1000000`).
- TT: `Map` keyed on Zobrist `lo`, entries `{ hi, side, depth, vec, move }` verified on `hi` + `side`, probe needs `depth >= depth`; every entry is EXACT (no bound flags without alpha-beta). `ZLO`/`ZHI` are `Int32Array(121·7)` LCG tables (seeds 0x7C4D9A31 / 0x2B8E1F63); `TT_LIMIT = 120000` (vectors weigh more than checkers' scalar entries). Incremental keying like the other engines: `zobrist(bd)` once at the root, two XOR lookups per move below.
- `aiPickMove(bd0, side, level, ms)` derives `seats` from the board values themselves (ascending ids present), so the Worker protocol stays exactly `{ id, board, side, level, ms } → { id, move }` with no extra fields; `move` is `{ from, to, path, gain, score }` or null. Iterative deepening d = 2 … `1 + (myMoves−1)·seats.length` (the ply horizon adapts to the seat count) under the usual TIMEOUT-symbol deadline on a private board copy, partially-scored depths discarded.
- `LEVELS[0..9]`: `{ label, myMoves, ms, noise, random, k, kOpp }` — `myMoves` 1→5 (own-move horizon), ms 60→1600. `random` is the chance of playing any **non-backward** move (`gain ≥ 0` pool; 0.8/0.4/0.1 at levels 1–3 then 0) — pure random would walk marbles backwards forever. Noise margin = `noise·3`, forced to 0 when a win (≥100000) is in hand. Labels are descriptive ("first games" … "grandmaster"); Elo is meaningless off 2-player.
- **No live eval / eval bar** (deliberate): a per-player score vector has no single number to paint; the game ignores the `engine-eval` flag.
- All of the above is executable: **`node test/chinese-checkers-engine.test.cjs`** (the repo's one test file — `.cjs` so a stray `"type": "module"` package.json above the repo can't break it; takes about a minute). It asserts the geometry invariants (121 cells, 10-cell triangles, 61-cell hexagon, 14 opening moves), the corner-resting rule (constructed position: a foreign corner rejects both a step and a hop landing while its owner can re-enter), all three anti-blocking states (squatters-only full ≠ win, full + ≥1 yours = win, no win at game start), strict team-win semantics (partner squatters never count; both partners must be done; another seat's move can't complete it), gift-refusal by the searching AI, and full self-play to a win at 2p/3p/4p/6p free-for-all plus 4p/6p teams. Self-play game length is very noisy at the near-greedy low levels (4p level 3 has finished anywhere from ~270 to >900 moves), which is why its cap is 3000 — a "stall" failure below a generous cap is usually just noise.
