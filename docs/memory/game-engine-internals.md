Engine internals (as of 2026-08-13) so difficulty/AI changes don't require re-reading the engine sections.

**Chess (`js/chess.js`, "Engine" section ~line 66):**
- `new Worker("engines/stockfish-18-lite-single.js")` (document-relative path). Plain UCI text protocol over `postMessage`; replies matched by an `expect(pred)` promise queue over `onmessage` lines. Boot sends `uci` and waits for `uciok`; worker construction fails on `file://` and shows a "serve over HTTP" message.
- Difficulty (`configureEngine(elo)`): Stockfish's calibrated floor is **1320 Elo** — at ≥1320 it uses `UCI_LimitStrength`/`UCI_Elo`; below that it uses `Skill Level` = `clamp(floor((elo-600)/100), 0, 7)`.
- Two extra weakening knobs: `moveTimeMs(elo)` scales 80ms→1000ms, and `randomMoveChance(elo)` blends in random legal moves below ~900 Elo (~88% random at the 200-Elo default) because Stockfish can't get weak enough alone.
- Live evaluation ("Live evaluation" section ~line 112, opt-in via the `engine-eval` storage flag): when enabled, the engine analyses continuously on the player's turn (`go infinite`, started after each player-facing render and stopped before every engine search) and the first `info … score` line received per position paints a lichess-style bar (`#eval`) under the board. Scores come back side-relative (`searchTurn` flips the sign); mate scores are stored as ±1e6 plus a signed mate count shown as `Mx`/`m-x`. `parseScore` rewrites `evalWhite`/`evalMate` on every line, so the bar tracks the deepening search in place. The eval bar never touches gameplay: `engineMove` always stops the analysis first (`stopAnalysis`), and game over frees the worker. `stopAnalysis` posts `stop` then drains the analysis `bestmove` via `drainBestmove()`, which abandons the wait after 1.5s (and removes its waiter) so a `go infinite` that never answers "stop" — seen around mating lines — can't hang the engine's next move.

**Checkers (rules + engine in `js/shared/checkers-engine.js`; `js/checkers.js` is the UI):**
- Board is `number[8][8]`: 1 red man, 2 red king, -1 black man, -2 black king, 0 empty. `RED = 1`, `BLK = -1`; red starts at the bottom (rows 5–7), moves up (decreasing row), and moves first. Kings crown at `CROWN_ROW = { RED: 0, BLK: 7 }`. 80 plies without capture/man-move = draw (checked by `js/checkers.js`, not the engine).
- Engine: negamax + alpha-beta + iterative deepening from depth 2, plus a **transposition table** (`Map`, Zobrist-keyed; two independent deterministic 32-bit LCG tables `ZLO`/`ZHI` make a 64-bit key, Map keyed on `lo` with `hi` verified on hit so a collision is a miss, never a wrong move; capped at `TT_LIMIT = 200000` and cleared when full). Entries store `{ side, depth, score, flag, move }` with `flag` 0 EXACT / 1 LOWER / 2 UPPER; probe returns on matching `side` + `depth >= depth`, and the stored best move is tried first for move ordering. Mate scores encode distance-to-mate as remaining depth (`-50000 - depth` for a no-moves loss — later losses score less negative, quicker wins higher), so probes re-base scores with `|score| > 40000` by `ent.depth - depth` to keep distances comparable (both engines, added 2026-08-13). `negamax` also enforces a `performance.now()` deadline by throwing a `TIMEOUT` symbol (search runs on a private board copy because the throw skips `undoMove`). Quiescence: depth 0 keeps resolving forced captures. `evaluate` is material (man 100, king 175) + advancement + center bonus, positive = good for red.
- Both the AI's move and the live eval run through the same Worker (`askEngine` in `js/checkers.js`; protocol `{ id, board, side, level, ms } → { id, move }`), sharing the one transposition table — so the eval search warms the AI's next move. If the Worker can't start (e.g. `file://`), `askEngine` degrades to calling `aiPickMove` synchronously on the main thread.
- `LEVELS[0..9]` table drives the 10 difficulty levels: `{ label, depth, ms, noise, random }` — depth 1→15, time budget 60→2000ms (ramped up from 60→1300ms; high levels are time-capped, not depth-capped — at 2s level 10 reaches effective depth ~8–11 in middlegames vs depth 3 for level 4, and extra budget beyond ~1s buys little because per-ply cost grows exponentially), `noise` widens the pool of near-best moves picked from at random, `random` is the chance of playing any legal move (0.85 at level 1, 0 from level 4 up) so young kids can win. Iterative deepening caps at the level's `depth`. The noise margin drops to 0 when the best score is decisive (`|score| ≥ 40000`) — win/loss scores differ by only 2 per ply, so noise used to lump every losing move together and a lost AI played randomly instead of blocking (both engines, fixed 2026-08-13).
- Live evaluation ("Live evaluation" section in `js/checkers.js`, opt-in via the `engine-eval` storage flag): the player's turn ends by scheduling `quickEval` 250ms after the "Your move" render. It calls `askEngine(playerSide, EVAL_LEVEL, EVAL_MS)` — `EVAL_LEVEL = 9` (LEVELS[9]: depth 15, though the `EVAL_MS = 300` short override is what actually bounds it, so a pending eval never delays the AI's own move request queued behind it) — and paints the reply's `.score` on the `#eval` bar (side-to-move-relative, which on the player's turn means player-relative; `random` is 0 at that level so the score is exact minimax). Stale replies are dropped via a `gameSeq` counter bumped on start/undo. Fixed 2026-08-13: `paintEval` used to negate the score for a Black player, showing the bar backwards — the score is used as-is now.

**Connect Four (rules + engine in `js/shared/connect4-engine.js`; `js/connect4.js` is the UI):**
- Board is `number[6][7]`: 1 red, -1 yellow, 0 empty; `board[0]` is the TOP row and a disc lands on the highest-indexed empty row (`landingRow`). `RED = 1` moves first. Draw = full board (no move clock). `winLine(bd, r, c)` returns the winning cells through (r,c) for the UI's highlight; `isWinAt` is the allocation-free variant the search uses.
- Engine: deliberately the same architecture as checkers — negamax + alpha-beta + iterative deepening from depth 2, TIMEOUT-symbol deadline on a private board copy, and a Zobrist transposition table (`ZLO`/`ZHI` 32-bit LCG pairs, Map keyed on `lo` with `hi` verified, `TT_LIMIT = 200000`, entries `{ side, depth, score, flag, move: col }`). Moves are generated centre-first (`ORDER = [3,2,4,1,5,0,6]`) for sharper cuts. Each node first checks whether any legal reply wins on the spot and returns `50000 + depth` (prefers faster wins and later losses, keeps the search out of finished positions); an immediate root win scores `1000000`. TT probes re-base mate scores and the noise margin skips decisive scores, exactly as in checkers (see above). `evaluate` scores every 4-cell window only one side occupies (three = ±50, two = ±10, one = ±1) plus ±5 per centre-column disc; positive = good for red.
- Worker protocol identical to checkers: `{ id, board, side, level, ms } → { id, move }` where `move` is `{ col, row, score }` or null (`score` is the best root score, side-to-move-relative); same `askEngine` wrapper and sync `aiPickMove` fallback for `file://` in `js/connect4.js`.
- `LEVELS[0..15]` — **16 levels** (was 10, widened 2026-08-13; `connect4.html`'s slider is `max="15"` and `js/index.js` prints "of 16"). `{ label, depth, ms, noise, random }` — depth 1→42 (42 = every square, i.e. perfect play if a search ever finishes it), time budget 60→4500ms, `random` fading 0.90/0.70/0.45/0.28/0.15/0.07 over levels 1-6 then 0, noise 240→0. Noise margin = `noise * 3` around the best score (0 when the best score is decisive). Labels are descriptive ("beginner"…"good luck!"), not Elo. Old saved prefs stay valid because the level is just an index that still exists; levels don't map 1:1 to the old table (old 10 ≈ new 13).
- The UI shortcuts forced replies: `obviousMove()` in `js/connect4.js` tries every legal column for both sides and, if anyone would make four in a row, passes `ms = min(level.ms, 400)` to `askEngine` and skips the hand's wavering. Verified 2026-08-13 that a 400ms cap picks the same blocking column as the full 4500ms level-16 search (the reply is forced, so depth can't change it), and that an available win returns in ~0ms via the root `1000000` shortcut.
- Live eval mirrors checkers: `EVAL_LEVEL = 10` (LEVELS[10]: depth 14), `EVAL_MS = 300`, 250ms `scheduleEval` delay, `gameSeq` staleness guard; the bar maps score via `100/(1+e^(-0.01·mine))` clamped to 3–97% and shows a text callout instead of a number when `|score| ≥ 40000` (forced win found).
